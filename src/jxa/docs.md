# Noridoc: jxa

Path: @/src/jxa

### Overview

- Contains the sole JXA (JavaScript for Automation) bridge script that communicates with OmniFocus.app via Apple Events.
- Executes as a standalone `osascript` process — receives a JSON command string as argv, returns a JSON result string.
- Purely synchronous; no async, no imports, no module system — constrained by the JXA runtime.

### How it fits into the larger codebase

- Invoked exclusively by `@/src/core/bridge.ts`, which shells out via `osascript -l JavaScript` and passes the command JSON as the first argument.
- Every CLI command in `@/src/commands/` ultimately bottlenecks through this single file — it is the only code that touches OmniFocus.app.
- Returns structured JSON that `bridge.ts` parses into typed `BridgeResponse<T>` objects for the rest of the TypeScript codebase to consume.
- The operation namespace (e.g. `task.create`, `project.get`) forms a stable contract between the TypeScript client layer and this script; adding a new CLI command that needs OmniFocus data means registering a new handler here.

### Core Implementation

- **JSON protocol**: Input is `{ op, params }`. Output is always `{ ok: true, data }` on success or `{ ok: false, error, candidates? }` on failure. The `candidates` field appears when entity lookup is ambiguous, enabling the CLI to present choices.
- **Dispatcher**: The `run(args)` entry point resolves the command JSON, obtains the OmniFocus `Application` and its `defaultDocument`, looks up a handler in the `ops` registry by `cmd.op`, and calls `handler(of, doc, params)`. Unrecognized ops and uncaught exceptions are caught and returned as `fail()` responses. Acquiring the `Application('OmniFocus')` handle is itself wrapped in try/catch — if OmniFocus isn't installed or can't be opened, `run()` returns a structured `fail("OmniFocus could not be opened: ...")` instead of letting the exception propagate to raw, unfriendly osascript stderr.
- **`@stdin` sentinel for large commands**: when `args[0]` is the literal string `"@stdin"`, `run()` calls `readCommandFromStdin()` instead of using the argv value directly — it reads the process's stdin to EOF via the ObjC bridge (`$.NSFileHandle.fileHandleWithStandardInput.readDataToEndOfFile`, decoded as a UTF-8 `NSString`) and throws if the bytes don't decode. This exists because argv has a hard OS size limit (`ARG_MAX`) that large bulk-operation payloads or huge task notes can exceed; `@/src/core/bridge.ts` decides per-call whether to use the sentinel. Plain argv commands are unaffected.
- **Ops registry**: A plain `var ops = {}` object where each handler is registered as `ops["domain.action"] = function(of, doc, p) { ... }`. Domains include `task`, `project`, `tag`, `folder`, `inbox`, plus top-level ops like `forecast`, `review`, `stats`, `bulk.*`, and `collect`. Notification CRUD is exposed via `task.notification.*`.
- **Fuzzy entity resolution**: Lookup functions (`findExistingTag`, `findExistingProject`, `findTaskByQuery`) follow a consistent three-tier strategy: exact match → case-insensitive substring match → ambiguity error with up to 10 candidate names. `findTaskByQuery` adds an ID-based lookup as the first tier.
- **Batch property access is required, not just an optimization**: `task.list` (both the inbox and non-inbox branches), `stats`, and `task.search` fetch each needed property as a whole array in one call (e.g. `doc.flattenedTasks.completed()`, `ft.dueDate()`) and index into the arrays, instead of calling a property accessor per task per property. On large databases (thousands of tasks), the per-task-per-property form issues one Apple Event per call and times out — `stats` and `task list --filter overdue` were unusable (60s/30s timeouts) before this was applied; `forecast`/`review` already used the batch form. `formatTask()` is only invoked for tasks that already passed the filter, using a lazily-materialized `ft()` element-array reference for the final read. The same correctness requirement (not just an optimization) applies to `formatProject()`/`project.list --full`, `tag.list --count`, and `tag.tasks` — see the per-project and per-tag bullets below for the specific fixes and timings.
- **The same batch pattern applies per-project, not just at the document root**: `formatProject()` (used by `project.get` and `project.list --full`), `project.get`'s `overdueCount`, and `project.list`'s `activeOnly` filter each used to materialize `project.flattenedTasks()` and loop `tasks[i].completed()` (plus `dueDate()`) per task — with ~130 projects, a large multiple of per-task Apple Events, and `project list --full --json` timed out at 30s. All three now read `project.flattenedTasks` as a bare property (a specifier, not materialized refs) and batch `.completed()`/`.dueDate()` once per project, indexing the returned arrays. `formatProjectCompact()` follows suit for its task count (`project.flattenedTasks.completed().length`) to avoid materializing refs just to read `.length`.
- **And per-tag**: `tag.list`'s `activeOnly` check and `count` branch, plus `tag.tasks`, used to materialize `tag.tasks()` once and then loop `.completed()` per materialized task ref — on the live ~3k-task database `tag list --count` took 22.3s and `tag tasks <name>` took 12.3s for 32 results. Both now batch-read `tag.tasks.completed()` (the bare `tasks` specifier, not `tag.tasks()`) once per tag/lookup and derive counts/survivor indices from that array; `tag.tasks` only materializes `refs = lookup.tag.tasks()` lazily, the first time a surviving (incomplete) index needs `formatTask()`. `review`'s "Active project progress" loop had the identical per-task-per-project pattern (`pj.flattenedTasks()` materialized, then `.completed()` looped per task) and was fixed the same way: `pj.flattenedTasks.completed()` batch-read once per active project. Live timings after the fix: `tag list --count` ~3.6s (was 22.3s), `tag tasks` ~9s for 32 results (was 12.3s — the remaining time is `formatTask()`'s inherent per-survivor Apple Event cost, not a batch-filtering cost), `review --days 7` ~5.6s.
- **`forecast` filters on effective status, not just the task's own `completed` flag**: a task inside a completed or dropped project (or parent task) keeps `completed === false` — only `effectivelyCompleted`/`effectivelyDropped` reflect the container's state, and OmniFocus's own Forecast hides such tasks. The op batch-reads both effective arrays (each guarded by try/catch falling back to `[]`, like `plannedDate`) and skips any task where either is true, so marking a project done immediately clears its leftover children from every forecast bucket and from drag alerts. Without this, incomplete children of completed projects showed up as phantom overdue tasks. Note the other read ops (`task.list`, `task.search`, `stats`) still filter on the plain `completed` flag only.
- **`createTaskRecord(of, doc, p)`** builds one task from a parameter bag and is shared by `ops["task.create"]` and `ops["bulk.create"]`: it rejects `project` and `parent`/`parentId` given together (`"Use either project or parent, not both"`), resolves `parentId` via `findTaskById` or `parent` via `findTaskByQuery` (propagating that lookup's own `candidates` on ambiguity) or `project` via `findExistingProject`, creates the `of.Task` under the parent/project or an `of.InboxTask` in the inbox, then calls `applyTaskProps` and returns `{ data }` (with `data.parent = { id, name, project }` when nested) or `{ error, candidates? }`. Because both ops funnel through it, a parent/subtask is honored in `bulk add` exactly as in `task add` — there is no separate `task.subtask` or `inbox.add` op; the CLI's former `task subtask`/`inbox add` commands were removed in favor of `task add --parent`/`--parent-id` (see `@/src/commands/docs.md`), and `bulk.create` is the bridge op still backing the renamed `bulk add` CLI verb.
- **Property application**: `applyTaskProps` is a shared function that batch-applies a parameter bag (due, defer, flag, tags, repeat, estimate, etc.) to a task, returning an array of human-readable change descriptions. Tag and repeat operations that fail are recorded as soft warnings rather than aborting the operation. For due/defer/planned it resolves through `resolveDate` (below) and pushes a change string of the form `due: <input> → <local iso>` rather than echoing the raw input, so callers can see what the natural-language text actually resolved to. Because `applyTaskProps` is shared, `task.create`, `task.update`, `bulk.*`, and `inbox.process` all get natural-language due/defer/planned dates for free.
- **Smart date resolution** (`resolveDate(of, input, field)`, `field` is `"due"` | `"defer"` | `"planned"`): input matching `ISO_DATE_RE` (`YYYY-MM-DD` or `YYYY-MM-DDTHH:mm`) is parsed with the original, unchanged `parseDate` — this preserves old behavior byte-for-byte (a bare ISO date still lands at local midnight) so existing scripts and the agent skill see no difference. Anything else goes through `omniParseDate`, which runs an Omni Automation script via `runOmniAutomation` (the same helper notifications use — see below) calling `Formatter.Date.withStyle(Short, Short).dateFromString(...)`, the identical parser behind OmniFocus's own date fields (handles "tomorrow", "fri 5pm", "2d", "1w", "next week", "10.9.", "noon", and returns null for unparseable text), and also reads the app's `DefaultDueTime`/`DefaultStartTime`/`DefaultPlannedTime` settings. If the parsed date lands at local midnight *and* the input has no explicit time token (`EXPLICIT_TIME_RE`: `HH:MM`, `5pm`, `noon`, `midnight`, `midday`), `applyDefaultTime` applies the field's default time — mirroring what typing the same text into the app's date field does. Unparseable input throws `Could not understand date "<input>". Try e.g. ...`; an Omni Automation failure throws `Could not parse date "<input>": <error>`. `parseDate` itself is now only ever called from inside `resolveDate`.
- **Read-back verification on date writes** (`setDateProp(task, prop, label, date)`): assigns the JXA property, immediately reads it back, and throws `OmniFocus did not store the <label> <local-iso> (task still reports ...)` if the stored value is missing or differs by a minute or more from what was requested. This is a deliberate invariant — OmniFocus can silently refuse to store a date change (e.g. a repeating task's rule overriding it), and without the read-back check the bridge would report success anyway. `formatLocalIso(date)` renders `YYYY-MM-DDTHH:mm` in local wall-clock time and is used both in this error and in `applyTaskProps`'s change strings.
- **Notification bridge path**: Task notifications are implemented through `of.evaluateJavascript(...)` (Omni Automation `Task.Notification`) because Apple Event task objects do not expose notification properties directly. Offset/repeat-interval params are checked with `!= null`, not truthiness, so an explicit `0` (e.g. a due-relative offset of "fire exactly at the due date") is applied rather than treated as unset; a `repeatIntervalSeconds` of `0` is itself Omni Automation's own sentinel for "do not repeat." `runOmniAutomation(of, payload, scriptBody)` is the shared low-level helper behind this — it now also backs `omniParseDate` above, so it has two independent callers (notification CRUD and date parsing) rather than one.
- **`limit` caps returned results, not the scan window**: `task.list` (inbox and non-inbox branches) scans until it has collected `limit` matching results rather than stopping after scanning `limit` raw entries. `doc.inboxTasks` keeps completed tasks until cleanup, and they can occupy the front of the collection — capping the scan window instead of the result count previously caused `inbox list --limit N` to return an empty list on databases with enough completed tasks up front. `task.list` also validates the filter name before entering the loop, so an unknown filter fails immediately even against an empty database.
- **Inbox default limit is 50, not 500**: both `task.list`'s inbox-filter fallback and `inbox.list`'s own fallback default to 50 when no `limit` param is sent. This keeps an unfiltered `inbox list` from dumping thousands of lines of JSON into a caller's context (an agent-friendliness concern, not just a performance one — the callers most likely to omit `--limit` are LLM agents).
- **`newestFirst` sorts before limiting, not after**: `task.list`'s inbox branch builds an `order` array of incomplete-item indices, and when `p.newestFirst` is set, sorts that index array by batch-read `inbox.creationDate()` (descending) before the result loop applies `limit`. Because `doc.inboxTasks` is otherwise in OmniFocus document order (oldest first), this is the only way to get "the N most recently captured items" without fetching everything and sorting client-side. `inbox.list` forwards `p.newestFirst` straight through to `task.list`. The per-task `creationDate` read was folded into this same batch (`inbox.creationDate()`) rather than read per-task inside the result-formatting loop, saving one Apple Event per task in the inbox branch regardless of `newestFirst`.

### Things to Know

- **Defensive property access everywhere**: Nearly every JXA property read is wrapped in `try/catch` because OmniFocus objects can throw when properties are inaccessible (e.g., `effectiveDueDate` on tasks in certain states, `plannedDate` on older OmniFocus versions). The catch blocks return safe defaults (`null`, `false`, `0`). This "risky reads return safe defaults" convention extends to batch reads too: `task.search` falls back to name-only matching if its note batch read (`ft.note()`) throws (caught to `[]`), and `tag.tasks` returns an empty list if its completed batch read (`lookup.tag.tasks.completed()`) throws (caught to `[]`) — both degrade silently rather than failing the op.
- **Soft failure in batch operations**: `bulk.create`, `bulk.update`, and `bulk.complete` process each item independently, collecting per-item `{ ok, ... }` results. A single item failure does not abort the batch.
- **ISO dates still parse manually; everything else goes through OmniFocus's own parser**: `parseDate` handles `YYYY-MM-DD` and `YYYY-MM-DDTHH:MM` formats explicitly with string splitting (no `Date.parse`) to avoid timezone ambiguity in the JXA runtime, but it is now reached only via `resolveDate`'s ISO-format branch. Natural-language input (`"tomorrow"`, `"fri 5pm"`, `"2d"`, ...) is delegated to Omni Automation's `Formatter.Date` rather than parsed by hand — see the Core Implementation bullets above for `resolveDate`/`omniParseDate`/`setDateProp`.
- **No ES6**: The entire file uses `var`, `function`, and `for` loops — JXA's JavaScript engine is pre-ES6. No `let`/`const`, arrow functions, template literals, or destructuring.
- **Strict capability behavior for notifications**: notification-enabled read/mutation paths fail explicitly if the OmniFocus runtime does not support `Task.Notification`.
- **`collect` op returns plain completed-task records**: no enrichment or parsing of task names/tags — just the standard fields (`omnifocus_id`, `name`, `project`, `completion_date`, `tags`, `estimated_minutes`, `note`) for each completed task in the lookback window.
- **Ambiguity is an error, not a guess**: When multiple entities match a fuzzy lookup, the bridge returns an error with candidates rather than silently picking one. This is a deliberate design invariant that pushes disambiguation to the CLI layer.
- **Destructive ops double-guard on `confirm`**: `task.delete`, `project.delete`, `tag.delete`, and the delete branch of `ops["inbox.process"]` all require `p.confirm` to be truthy and return `fail("...requires confirm: true for safety")` otherwise, even though the CLI layer already enforces `--confirm` before sending the command. This is deliberate defense-in-depth — the bridge does not trust the CLI layer alone. In `inbox.process`, the confirm check runs after the `dryRun` early-return, so `--dry-run --delete` never touches the guard.
- **`stats.tasks.inbox` counts only unprocessed inbox items**: it filters `doc.inboxTasks` down to incomplete entries (via batch `.completed()`) rather than reporting the raw `inboxTasks` count, which includes completed items lingering until cleanup and would otherwise overstate the unprocessed inbox size.
- **`task.complete` disambiguates "not found" from "already in that state"**: `findTaskByQuery` filters by completion state (incomplete-only by default), and `task.search`/`task.list` hide completed tasks entirely — so for a name query (not `--id`), a bare "not found" was ambiguous between "this task doesn't exist" and "it's already completed," which matters most to an agent caller told to complete a task it already finished. When the initial lookup fails with no ambiguity candidates, `ops["task.complete"]` retries `findTaskByQuery` with the opposite `searchCompleted` state: a single opposite-state match returns a distinct error (`Task already completed: "..." (completed <ISO date>) (id: ...)` or, when reopening via `--incomplete`, `Task is already incomplete: "..." (id: ...)`); multiple opposite-state matches return `No incomplete/completed task matches "...", but completed/incomplete tasks do` with `candidates`; no match in either state falls through to the original plain `Task not found`. Ambiguity among same-state matches is unaffected — the fallback only fires when the first lookup's error has no candidates.
- **`whose()` predicate cost scales with match count, not with `limit`**: `task.search` previously used `doc.flattenedTasks.whose({ name: { _contains: query } })` to find matches. On a large database, a broad or user-supplied query (e.g. a single common letter) can match a large fraction of all tasks, and `whose()` evaluation itself times out before a single result is read or formatted — this is independent of, and precedes, the per-element property-read cost described above. There is no way to bound this cost via `limit`, since `whose()` has to finish matching before any limiting happens. The fix was to stop using `whose()` for this op entirely: batch-read `name()`/`note()`/`completed()`/`id()` across the unfiltered `doc.flattenedTasks` and do substring matching, completed-filtering, and id-dedup in plain JS, only materializing `formatTask()` for indices that survive. Any new op that filters on a predicate that could match a large, unbounded portion of the database should use this JS-side-filter pattern rather than `whose()`.
